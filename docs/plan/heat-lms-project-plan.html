02 · Decisions

Design decisions I am proposing

These choices shape the whole backlog, so I want them agreed before issues are written. Each will become an Architecture Decision Record in docs/adr/.

D1

pnpm + Turborepo monorepo with shared contracts

Two Next.js apps, the NestJS API and the worker live in one repo. A single @heat/contracts package holds Zod schemas used by React Hook Form in the browser and by nestjs-zod in the API, so frontend and backend validation cannot drift.

D2

Modular monolith API, separate worker process

NestJS modules with strict boundaries. The worker is the same codebase started with a different entry point and runs BullMQ consumers (transcode, certificate, email, cleanup), so FFmpeg never shares a process with HTTP traffic. No microservices, Kubernetes or Kafka.

D3

First-party cookie sessions, two realms

Nginx routes /api on both hosts to NestJS, and blocks admin API paths on the student host. The access cookie (10 minutes) and the CSRF cookie use the __Host- prefix; the access cookie is SameSite=Lax so links from emails arrive signed in. The refresh cookie uses the __Secure- prefix with no Domain, is SameSite=Strict and is limited to the refresh path (a __Host- cookie cannot be path-limited). A rotating refresh token is stored hashed, with reuse detection and a 20-second grace window for parallel refreshes. CSRF tokens are HMAC-bound to the session, so a sibling subdomain cannot plant one. Passwords use argon2id. Student and admin tokens carry different audiences. Admins must use an authenticator-app code (TOTP) with recovery codes; deactivating an admin revokes their sessions immediately, and a break-glass command on the server restores super-admin access if the authenticator is lost.

D4

Content lock with course revisions

A course moves from DRAFT to PUBLISHED. Publishing is refused unless every module has a ready video and a quiz with at least one question. The lock is taken inside the first approval's transaction, so it cannot race an admin edit: modules, videos, answer options, correct answers, quiz rules and pass marks become read-only. Wording fixes stay allowed but are limited to text changes that keep the same structure (no added or removed images, links, sections or questions), and each one is stored as a before/after diff in the audit log. Description, thumbnail, tags and front-page order stay editable. Bigger changes go into a cloned draft revision; enrollments are pinned to a revision at approval time, and shared video assets are reference-counted so cleanup never deletes a video another revision uses.

D5

Signed HLS delivered by Nginx, never proxied through Node

The API issues a playback session and sets a short-lived HMAC-signed cookie scoped to /hls/<videoId>/. Nginx (njs) verifies the signature on every playlist and segment without touching the database. Originals stay outside the web root. A Phase 1 spike proves this on the real VPS before anything else depends on it.

D6

Watched-interval progress the server can trust

The player sends watched ranges every 15 s and on pause, seek or tab hide. The server accepts ranges only up to the wall-clock time since the playback session started, multiplied by the highest allowed playback speed, so a script cannot report a whole video as watched. Late batches from an offline retry are accepted within that same budget. A video counts as complete at ≥ 80% coverage. Resume position is stored separately and never moves backwards from a stale request. Heartbeats are batched writes; Redis buffering is added only if load tests show a need.

D7

Transactional outbox for email and jobs

Domain events (enrolled, verified, completed) are written to an Outbox table in the same transaction as the state change, then relayed to BullMQ. No email or certificate is lost if Redis restarts, and none is sent twice.

D8

Certificate PDFs from an HTML template

Names are entered in English, so any PDF approach works. Rendering an HTML template in Playwright Chromium inside the worker keeps the certificate design a normal web template that matches the site, and leaves room for Bangla text later. Each certificate gets a random number, a QR code linking to the verification page, and a stored SHA-256 of the file.

D9

Bangla and English interface from day one

The demo has a বাংলা / English toggle. Interface strings and emails go through next-intl from the first screen, so translation is never a retrofit. Course content is in one language per course, with the schema ready for translations later.

D10

Hooks guide, CI and branch protection enforce

Claude Code hooks are shell commands that run on events, and some can be bypassed through other tools. An /implement-issue skill drives the eight stages (section 12), hooks act as guard rails, and the hard gates are branch protection and CI: nothing merges without green checks, and only you merge.

D11

Enrollment approval lifecycle

Status moves PENDING_VERIFICATION → PENDING_APPROVAL → APPROVED → COMPLETED, or to REJECTED, EXPIRED or REMOVED. Content endpoints and playback sessions allow APPROVED and COMPLETED; a removed student loses video access within one cookie lifetime (10 minutes). Removal is possible from either state, and reinstatement restores the state the student had. Rejection soft-deletes the account only when no other approved or completed enrollment exists. Email jobs store a copy of the recipient address, so the rejection email still goes out after the account is hidden. A new registration for an email that only has an unverified account replaces that account, and verifying an email signs out every session created before verification, so nobody can squat or pre-hijack an account. Registering an email that already has an account shows the normal success message and sends that address an “you already have an account” email, so the form never reveals who has enrolled.

D12

Pluggable, quota-aware email

A MailTransport interface with an SMTP implementation chosen by configuration; personal Gmail first. All mail goes through a BullMQ queue with a Redis counter for the rolling 24-hour limit, split into per-category budgets so verification, password codes and resets always have capacity before approval and certificate mail. When a budget is used up, jobs wait until it frees instead of failing; Gmail quota errors (550 5.4.5) pause the queue the same way. Resend-verification and forgot-password require the captcha and are capped per email. The 7-day expiry for unverified registrations starts when the verification email is actually sent. Gmail SMTP gives no bounce reports, so failures are tracked from SMTP responses only.

D13

One component library, minimal CSS

@heat/ui is the only place styles are written: shadcn components themed by design tokens, plus composite components shared by both apps (page header, data table, form field, status badge, empty state, confirm dialog, stat card, file upload). Apps compose these and use Tailwind only for layout. No one-off CSS files, no arbitrary values outside the tokens, and no component on a screen unless the task needs it.

D14

Insights from daily rollups, not live scans

A nightly BullMQ job (plus an on-demand refresh) aggregates enrollments, module progress and quiz attempts into small rollup tables by day, course, module and academic group. The Insights page reads only these rollups, so charts load fast and never slow down students. Only aggregates are shown, groups smaller than 5 students are hidden, and the same data powers CSV download of each chart. Event timestamps are recorded from day one so later insights (video engagement, activity) need no backfill.

D15

One data path per kind of page

Public pages render on the server and are cached by tag; signed-in pages check the session in a server-only data layer and prefetch on the server; all interactive calls go from the browser to the API through generated hooks. No Server Actions. Sessions refresh in proxy.ts. Details in the Frontend design section.

D16

Images and files on local disk behind a storage interface

Uploads are type-checked, stripped and resized once, then stored under random names with a visibility level: public, protected (signed 1-hour links) or private (API-checked). Content stores asset IDs, not links, so a cloud S3 driver or CDN can be added later. MinIO was rejected.

Every browser request goes through Nginx on the app's own host, so cookies stay first-party.

Rules

  • Public pages render on the server and are cached by tag. When an admin changes content, the API tells frontend-public which tags to refresh.
  • Signed-in pages check the session in a server-only data layer on every page. Checks are never only in a layout. First data is fetched on the server and handed to TanStack Query.
  • Everything interactive calls the API from the browser through hooks generated by orval from the API's OpenAPI spec. No Server Actions, so there is one path for auth and CSRF.
  • Sessions are refreshed in proxy.ts before a page renders, and by one shared retry in the browser. The API allows a 20-second grace window so parallel refreshes never log anyone out.

Shared packages

  • @heat/ui: the only place styles are written
  • @heat/contracts: Zod schemas and error codes, used by the forms and the API
  • @heat/api-client: generated hooks, request wrapper and server fetcher
  • @heat/i18n: Bangla and English text for the student app and emails
  • A CI check fails the build when the generated client is out of date with the API.

Access is checked per course. Approved and completed students can open a course; a completed student can rewatch lessons and see past quiz results. Pending courses show their status, removed courses show the reason, and a signed-in student can request further courses with one click.

Student experience

Video player

  • Video.js v10 on hls.js, styled through the shared theme
  • Auto quality capped at 480p on data-saver or 2G/3G, otherwise 720p; 1080p available by hand
  • About 20 s buffered ahead, remembered quality and bandwidth
  • Resumes from the saved position; recovers from an expired video cookie without stopping
  • Bangla and English labels, keyboard shortcuts, optional captions

Progress and quiz

  • Watched ranges sent every 15 s and on pause, seek or tab hide; unsent ones retried after reconnecting
  • Quiz opens at 80% watched
  • Answers saved on the device while in progress; submission can be safely retried
  • Result screen with score, explanations after a pass, and a countdown before the next attempt

Slow-network budget

  • Public pages: at most 150 KB of JavaScript (gzipped) on first load
  • Learner pages: at most 200 KB, plus the player only on lesson pages
  • Largest content shown within 2.5 s on a mid-range Android over Slow 4G, checked in CI
  • Pre-sized images, self-hosted fonts, no third-party scripts

Admin experience

  • One data table for every list: server-side paging, sorting and filters kept in the address, so views can be shared and bookmarked. It turns into cards on phones.
  • One form pattern for create and edit, with an unsaved-changes guard and named confirmations for deletes.
  • Locked course fields are read-only with a short explanation; wording-fix fields note that changes are logged.
  • Drag to reorder modules and questions, with Move up / Move down for keyboard users.
  • Resumable video upload with pause and resume, then live processing status.
  • Insights charts share one filter bar, and each chart's data can be downloaded as CSV.
  • Course preview uses the same player and lesson components students see, with correct answers shown.

Shared building blocks: app shell, page header, data table, filter bar, form field, status badge, empty and error states, confirm dialog, stat card, chart card, file upload, video player, rich-text editor and renderer, sortable list, captcha field, language, theme and notification controls.

  • No inline styles, and no arbitrary Tailwind values outside @heat/ui

  • Every element must serve the screen's task: no filler cards, banners or stat tiles
  • Every component has a Storybook story in light and dark, Bangla and English, and passes an accessibility check

Images and files

WhatWho can see itHow it is served
Course and module thumbnails, news images, resourcesEveryonePublic link served directly by Nginx, cached for a year
Images inside lesson textApproved and completed students of that course, adminsLink that expires in 1 hour, checked by Nginx like the videos
Caption filesSame as the videoStored under the video's signed path and covered by the same playback cookie
Profile pictures, certificate PDFsThe owner and adminsThe API checks access, then Nginx sends the file
HEAT, partner and University of Dhaka logosEveryoneStatic files in the apps
  1. The API checks each upload's real type from its contents. JPEG, PNG, WebP and AVIF images, PDF, DOCX and PPTX documents, and WebVTT captions are allowed; SVG is rejected.
  2. Images are decoded, stripped of hidden data such as GPS location, and saved in fixed WebP sizes (320, 640, 1280 and 1920 px). The original upload is not kept.
  3. Files are stored on the server's disk under random names, behind a storage interface. Pages store the image's ID, never its link, so moving to cloud storage or a CDN later changes no content.
  4. Next.js picks the nearest ready-made size, so the server never resizes images while students browse.
  5. Unused uploads are deleted after 24 hours, and all files are in the nightly off-site backup.

Why not MinIO: its free edition stopped shipping in October 2025 and its repository was archived in 2026. On a single server it also adds a hop for every file without making files any safer.

Integrity rules

  • Unique (user, course) enrollment
  • Unique module order per revision, video order per module
  • One certificate per enrollment
  • RESTRICT on directory foreign keys
  • Department FK to the university-faculty pair
  • Email unique among non-deleted users only (partial unique index)

History is never rewritten

  • Attempts store passMarkSnapshot and the score
  • Enrollments are pinned to a revision
  • Soft delete (deletedAt) for rejected users, content and directory, filtered by a Prisma extension
  • Every approve, reject, remove and reinstate stored as an enrollment decision with admin and reason
  • Append-only audit log with actor, action, before and after

Security-relevant storage

  • Refresh, verification and reset tokens are stored as SHA-256 hashes only
  • Captcha answers live in Redis, hashed, with a TTL
  • Videos are referenced by assetKey, never by a disk path
  • Correct quiz options are never sent to the learner app
07 · Flows

Critical flows

The flows where a mistake costs the most: enrollment approval, video security, progress integrity and certificate issuance. Each gets integration tests that drive the real state machine.

Enrollment states

stateDiagram-v2
  [*] --> PENDING_VERIFICATION: form submitted
  PENDING_VERIFICATION --> PENDING_APPROVAL: email verified
  PENDING_VERIFICATION --> EXPIRED: 7 days unverified
  PENDING_APPROVAL --> APPROVED: admin approves
  PENDING_APPROVAL --> REJECTED: admin rejects
  APPROVED --> REMOVED: admin removes
  REMOVED --> APPROVED: admin reinstates
  COMPLETED --> REMOVED: admin removes
  REMOVED --> COMPLETED: reinstate if it was completed
  APPROVED --> COMPLETED: last module passed
  EXPIRED --> [*]
  REJECTED --> [*]

EXPIRED and REJECTED soft-delete the account only when it has no other approved or completed enrollment, which frees the email for a new registration. Approval, rejection and removal each send an email with the reason. Approval pins the enrollment to the current revision, locks the course and unlocks module 1 in one transaction.

Video processing states

stateDiagram-v2
  [*] --> UPLOADING
  UPLOADING --> UPLOADED: tus complete
  UPLOADED --> QUEUED: ffprobe ok
  UPLOADED --> REJECTED: bad codec or size
  QUEUED --> PROCESSING
  PROCESSING --> READY: renditions validated
  PROCESSING --> FAILED: error or timeout
  FAILED --> QUEUED: admin retry
  READY --> [*]

Each attempt writes to a fresh temp directory and swaps it in atomically, so a retry never mixes partial output. FFmpeg runs at low priority with concurrency 1.

RenditionTarget bitrate≈ size per 10 min
360p400 Kbps30 MB
480p650 Kbps49 MB
720p1.0–1.2 Mbps90 MB
1080p2.0–2.5 Mbps188 MB

H.264 video with AAC audio, about 6-second segments, keyframes aligned across renditions, and one master playlist listing every quality. A source smaller than 1080p is never upscaled. Bitrates are starting targets, tuned on real course footage in the Phase 1 spike.

Module progress states

stateDiagram-v2
  [*] --> LOCKED
  LOCKED --> UNLOCKED: previous module passed
  UNLOCKED --> IN_PROGRESS: first heartbeat
  IN_PROGRESS --> QUIZ_READY: required videos 80 pct
  QUIZ_READY --> COMPLETED: attempt passed
  QUIZ_READY --> QUIZ_READY: failed, wait, retry if allowed
  COMPLETED --> [*]

Module 1 unlocks when the enrollment is approved. If a quiz's attempt limit is used up, the module waits until an admin grants another attempt. Passing the last module marks the enrollment complete and writes a CertificateRequested outbox event, all in one transaction.

08 · Quality bar

Security and quality bar

The rules every ticket is reviewed against. They go into CLAUDE.md and the review agents' checklists, so the bar stays the same from the first ticket to the last.

Security

  • Target OWASP ASVS Level 2; checklist items linked from tickets
  • argon2id, breached-password check (k-anonymity), lockout with backoff
  • Rate limits on sign-in, enrollment, captcha, reset, verify and playback sessions, keyed by account or email plus IP with generous per-IP ceilings, because a whole campus or mobile carrier can share one IP
  • Worker isolation: certificate rendering in Chromium with networking off and an escaped template; FFmpeg limited to local files of that job
  • Nginx signed-link checks use the normalised path and a constant-time comparison, with key rotation
  • The audit log is append-only at the database level: the app's database user cannot update or delete its rows
  • Strict CSP with nonces, HSTS, helmet, CSRF double-submit for unsafe methods
  • Every endpoint has an explicit guard. Deny by default, with a test that fails on any unguarded route
  • Uploads checked by magic bytes and ffprobe, size-capped, stored outside the web root
  • Secrets only in environment files with restricted permissions; no secrets in images or the repo
  • Dependabot, CodeQL, pnpm audit and container scanning in CI

Engineering

  • TypeScript strict mode, no any, ESLint and Prettier enforced by hooks and CI
  • Test-driven work: unit tests for rules, integration tests on a real Postgres (Testcontainers), Playwright for user journeys
  • Coverage gate: 85% on domain services, 100% on unlock, scoring and certificate rules
  • Prisma migrations reviewed, never edited after merge, run with migrate deploy
  • Consistent error format with stable error codes shared through @heat/contracts
  • Structured logs with request ids, no personal data in logs

User experience

  • WCAG 2.2 AA: keyboard flows, focus states, contrast, captions support in the player
  • Bangla and English for every UI string
  • Performance budget on a mid-range Android over 4G: LCP under 2.5 s on public pages
  • Loading, empty and error states designed for every screen
  • Every screen built from @heat/ui components; no app-level CSS files and no values outside the tokens
  • No decorative or filler components: each element on a screen must help the task on that screen
  • Consistent patterns across both apps: the same table, form, dialog and feedback behaviour everywhere

Operations

  • SLO: 99.5% monthly availability, under 1% playback request failures
  • Continuous off-site archiving of the database write-ahead log (pgBackRest), so at most 15 minutes of data can be lost; nightly encrypted off-site backups of media and certificates; restore drill each month; recovery within 4 hours
  • Staging copy on the same VPS with resource limits; every release and migration runs there first
  • Migrations follow expand then contract (add, backfill, switch, remove later), so a deploy never breaks the running version
  • External uptime check that alerts when the server stops responding, since the dashboards run on the same server
  • All scheduled jobs and dates use Asia/Dhaka time
  • Dashboards: CPU steal, egress, disk latency, queue depth, Nginx 5xx, player errors
  • Runbooks for deploy, rollback, restore, disk full, bandwidth near quota and email quota reached
  • Email queue dashboard: sent today, remaining quota, delayed jobs, failures
09 · Roadmap

Delivery roadmap

Eight phases, one GitHub milestone each. Video delivery is proven in phase 1 because it is the part the VPS is most likely to struggle with. Each phase ends with exit criteria that are checked, not assumed.

P0Foundation

Repo, tooling, workflow

Monorepo, CI, Docker dev stack, CLAUDE.md, hooks, /implement-issue skill, issue templates, Open Pencil designs of the key screens and the theme, approved by you before any screen work, @heat/ui tokens.

Exit: a trivial ticket goes through all 8 workflow stages and merges green.

P1De-risk

Video delivery spike

Transcode real course footage, signed HLS through Nginx njs, minimal player, k6 test from outside the VPS.

Exit: 200 simulated viewers for 30 min on the target VPS with under 1% segment errors, or a documented change of plan.

P2Identity

Data model, auth, directory, enrollment, approval

Full Prisma schema, seed super admin, both auth realms with admin two-factor, captcha, university/faculty/department admin, minimal course and module admin with publish checks and the content lock, enrollment wizard, mail transport and email queue, email verification, approval queue with reject, remove and reinstate, notifications backend.

Exit: a student registers, verifies their email, is approved and sees their approved status; the first approval locks the course; rejection frees the email; the Gmail limit is simulated and queued mail resumes after reset.

P3Authoring

Full course admin, video pipeline, landing page

Revisions, lesson text, tags and front page, quiz builder, resumable upload, transcode jobs with live status, captions, media pipeline, the public landing and course pages.

Exit: an admin builds the full course, publishes it, the landing page shows it, and wording fixes work on a locked course.

P4Learning

Learner experience and assessment

Dashboard, course page, player with quality and speed controls, resume, interval progress, quiz taking, scoring and unlocks.

Exit: a student completes every module end to end in Playwright, and the unlock rules cannot be bypassed through the API.

P5Completion

Certificates, accounts, content, insights

Profile and avatar, password change and reset, certificate rendering and completion email, public verification, Resources, News & Updates and Contact pages, student detail, CSV export, summary dashboard and the Insights page.

Exit: completion produces exactly one certificate, emailed and verifiable by QR code; insights match a hand-checked sample dataset.

P6Hardening

Production readiness

VPS hardening, TLS, production compose, backups and restore drill, monitoring and alerts, security review, accessibility audit, full load test with mixed traffic.

Exit: acceptance criteria from the implementation plan met; restore drill passed; no open high-severity findings.

P7Launch

Pilot and launch

Content load by the department, pilot with one cohort, fixes, public launch, two weeks of close monitoring.

Exit: pilot cohort completes with no data-integrity incidents.

12 · Workflow

Claude delivery workflow

Each ticket goes through the same eight stages, started with /implement-issue <number>. The skill does the work; hooks stop it from skipping stages. Highlighted stages are where you can approve or take over.

  1. Pull ticket

    Fetch the issue, its epic, linked issues and comments with gh. Refuse if it is blocked or not ready.

    → issue context loaded

  2. Refine

    Refiner agent checks the ticket against the code and ADRs and appends a “Refined” section with acceptance criteria and edge cases. It never rewrites your original text.

    → issue updated, comment logged

  3. Branch

    Create feat/N-slug in its own worktree before anything is written, and move the card to In progress.

    → isolated workspace

  4. Brainstorm and plan

    Explore approaches, choose one, and write a step-by-step plan with tests first, committed on the branch. Optional human approval for L or security tickets.

    → docs/plans/issue-N.md, plan comment

  5. Implement (TDD)

    Failing test, code, refactor, in small conventional commits that reference the issue.

    → commits on branch

  6. Verify

    Lint, typecheck, unit, integration and affected Playwright tests. UI tickets are also checked in a real browser through Chrome DevTools.

    → verification log

  7. Code review

    Reviewer agent checks against the quality bar; the security agent runs for security or auth tickets. Findings are fixed and checks re-run.

    → review notes resolved

  8. Pull request

    PR with summary, test evidence, screenshots and Closes #N; card moves to In review. A human merges.

    → PR ready for merge

PR gatePreToolUse on BashBlocks gh pr create and pull-request API calls unless a verification marker newer than the last commit exists. Branch protection and CI remain the real gate.
FormatterPostToolUse on Edit / WriteRuns Prettier and ESLint fixes on the touched file.
Stop checkStopRuns the typecheck only, at most 3 times per turn, and respects stop_hook_active so it cannot loop. It skips the intentional failing-test step of TDD and pauses for plan approval; full tests run in the Verify stage and CI.

What keeps quality consistent across sessions

  • Short root CLAUDE.md pointing to per-app files and ADRs, so context stays focused
  • One reference implementation per pattern (a module, a form, a job) that new code copies
  • The plan file and issue comments are the memory between sessions, not the chat
  • Review agents read the same quality bar as the implementer

Where you stay in control

  • Approve the plan for large or security-sensitive tickets
  • Merge every PR; branch protection requires green CI and only you can merge
  • Lighthouse and screenshot checks warn on pull requests instead of blocking them, so a flaky check never stalls all work
  • Production deploys run only from tagged releases you create
  • ADR changes always go through you
